Hack & Build 2026 / Inclusive, evidence-first hiring

PIE Career Orchestrator

A multi-agent hiring system whose scores are computed before any language model is called, and whose matching agent is never given the attributes it must not use. This is what is actually built, and what is not.

Potential over pedigree  ·  AI recommends, recruiters decide

The load-bearing decision

The model never touches a number

Every capability score, match score, gap, bias signal and assessment result is computed by plain deterministic JavaScript in agents.js — no model involved, no randomness, same input, same output. Only once those numbers exist is a language model asked to put them into readable English.

This is not a stylistic preference. It is what lets PIE answer the question a hiring system has to answer: why. A recruiter can trace any number back to the evidence item that produced it. Swapping the model — or removing it entirely — changes the wording and not one figure.

Fairness by construction

What the matching agent is never given

Inclusion is enforced at the interface, not by asking a model to behave. The orchestrator hands the matching agent a role competency model and a set of skill confidences. Nineteen attributes are removed before the call, so the agent cannot weigh what it cannot see — and the Bias Audit service independently verifies that they were absent.

Assessment engine

Whose questions a candidate is asked

PIE's default is that questions are generated from the job description and the candidate's own evidence. That is a defensible default, not a mandate — a team with a question set they trust can take the judgement back. The mode is set per requisition and recorded on every attempt, because a score means something different under each one.

Every generated question is a candidate for inclusion, never a question. It passes schema, answer-key, ambiguity, relevance and duplicate checks before a candidate can see it. A question that fails is replaced, not repaired.

Coding answers are scored by running them. The previous grader matched rubric keywords in the text, and it was not merely weak — it was backwards: pasting the rubric's own words as a comment scored 100%, while a correct solution phrased differently scored 0. Keyword scoring is gone.
Assessment integrity

Defence in depth, and its limits stated

Face presence checks run in the browser using a 6 KB detector and its cascade, both served by the app — no CDN, so they work offline. PIE counts faces and measures how far the detected face moved between checks. There is no face recognition, no matching against a stored photo, and nothing about appearance is computed or stored.

A signal must hold for roughly two seconds before it is raised, with a twenty-second cooldown. With the breach threshold at three, a detector that complained on one bad frame would lock honest candidates out of their own assessment.

Reaching the threshold stops the attempt for human review. It never rejects anyone. The product describes itself as defence-in-depth assessment integrity — not as cheat-proof. Browser signals cannot see a second device, a person off camera, notes on paper, OS-level automation or a virtual machine, and PIE says so on the consent screen before a candidate agrees to anything.

Data

One system of record, one mirror

The JSON store is authoritative. Supabase receives writes in the background so the enterprise path is real rather than described — but nothing reads from it yet, and the Integrations page says exactly that rather than implying a live database.

Integrations

What is wired, and what is proven

Every state below is read from its adapter at request time. An adapter says Connected only after a real call has come back — having the credentials is never enough, and the Integrations page in the product shows the same states this table does.

ServiceClassificationWhat exists today
Corsair Proposed One shape for every third-party service: db for already-synced data, api for the live call. PIE reads GitHub evidence through it when configured. Promotes to Confirmed only when a real call succeeds.
GitHub Confirmed Repositories, languages and activity as supporting evidence. Three sources in order — Corsair's synced data, GitHub's own API, labelled demo fixtures — and PIE names the one it actually used.
Supabase Confirmed Durable accounts, evidence and decisions. Written through on every change and read back at boot, so an account outlives a restart on an ephemeral host.
Email (SMTP or HTTPS API) Confirmed Verification codes and reset links. Reports Verified only once a message has been accepted for delivery.
LLM provider Confirmed OpenAI, Gemini or a model you host yourself. Narration only — every score is identical with it or without it.
Why the plumbing is the interesting part. PIE's reasoning was never the hard bit. Getting a candidate's real work out of the tools they already use — OAuth per service, tokens to refresh, rate limits, a different client for every API — is what stands between an evidence-first hiring product and a form. Corsair collapses that into one shape, and its synced database turns evidence gathering from a fan-out of live calls into a local read.
